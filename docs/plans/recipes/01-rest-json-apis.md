**Target location:** `open_data/rest_apis/` (matches the `open_data/parquet_csv/` convention already established, rather than the manifest's originally-suggested `json/`)

## REST table DDL

Register the raw JSON response with `CREATE LIGHTNING REST TABLE ... REQUEST(...) HEADER(...) BODY()`, then flatten it with `CREATE SCHEMASTORE VIEW ... WITH CONTAINER <name> AS SELECT ... LATERAL VIEW explode(...)`. See `open_data/rest_apis/HOWTO.md` for the full syntax and examples.

1. **SEC EDGAR XBRL Company Facts API** — live-tested and working, `open_data/rest_apis/sql/rate_limited/01_edgar_company_facts_create.sql`, 7 companies (Apple, IBM, Oracle, Walmart, Target, Ford, Tesla). No signup, but requires a declared `User-Agent` (SEC blocks default ones) and respects a 10 req/sec rate limit. New addition, not in the original manifest.
2. **PokéAPI** — `sql/02_pokeapi_create.sql`. Open license (BSD-3-Clause), no signup, fair-use rate limiting. Live-tested and working (2026-09-19) — confirmed two-level nested dot-access through `explode()` works, extended to two Pokémon (Pikachu, Charizard) with abilities/types/stats views, cross-Pokémon `UNION ALL` views, and 6 example analytical queries.
3. **Open Food Facts — live single-product API** — `sql/03_open_food_facts_live_create.sql`. Open license, with a condition (ODbL). Distinct from the bulk CSV/JSONL export already pulled forward into the Parquet/CSV recipe — this is the live per-product REST lookup instead. Array-of-structs with sparse/optional fields per entry, plus a flat (non-array) nested struct (`nutriments`) with hyphenated field names. Expanded (2026-09-18) to four products (Nutella, Coca-Cola, Prince biscuits, Barilla Pesto) with nutrition + ingredients views and 8 analytical queries. Partially live-tested (2026-09-18) — queries 1-7 confirmed working; query 7 originally hit a Zetaris/Spark analyzer limitation (self-joining a UNION'd exploded view against an aggregate of itself) and was fixed and confirmed with a window-function rewrite, see `HOWTO.md`, "Troubleshooting / FAQ". Query 8 not yet reached.
4. **BLOCKED — Singapore data.gov.sg — PM2.5 real-time API** — moved to `failure_cases/singapore_pm25/04_singapore_pm25_create.sql`. Open license (SODL v1.0), no key needed for testing. Different shape class: array nested under a non-top-level wrapper key, fixed (non-array) struct per item. Expanded (2026-09-19) using the endpoint's `?date=` parameter to pull a full day of hourly readings (24 items) instead of just the latest one, added a region reference view and a long-format cross-region view, and 8 analytical queries. Also found and fixed a bug in the original script: it selected a `pm25_one_hourly.national` field that doesn't exist anywhere in the real response — the endpoint only returns the 5 regional readings, no national figure; replaced with a computed per-hour average across regions. Then hit a blocking issue: `CREATE LIGHTNING REST TABLE`, the first statement, returned an HTTP 502 with no other query run first. Independent `curl` testing ruled out headers/auth and found the endpoint's real rate limit is much tighter than documented (429 after ~5-6 requests in 5-8 seconds) — leading, unconfirmed hypothesis is Zetaris making more than one request per statement (schema introspection and/or a Data Explorer preview fetch) tripping that limit. Moved out of the main sequence into `open_data/rest_apis/failure_cases/singapore_pm25/`, full writeup in that directory's `ISSUE.md`, since the other 8 sources already cover the JSON-shape range this package needs.
5. **NASA NeoWs** (`/neo/browse`) — `sql/05_nasa_neows_create.sql`. Open license (public domain), `DEMO_KEY` works with no signup; confirmed (2026-09-19) this endpoint doesn't share Singapore's aggressive burst-throttling. Deeply nested array-of-structs plus a nested array-within-array, needing either indexing or a second `explode()`. Live-tested and working (2026-09-19) — base table and first view confirmed, then extended with a full-approach-history view (double `explode()`) and 8 analytical queries (largest/hazardous objects, closest/fastest approaches, most-tracked objects, a per-object closest-approach window function, and upcoming predicted approaches). Also surfaced a type gotcha: `miss_distance.kilometers` and `relative_velocity.kilometers_per_hour` are JSON strings, not numbers — every sort/aggregate on them uses an explicit `CAST(... AS DOUBLE)`, see `HOWTO.md`, "Troubleshooting / FAQ".
6. **NASA DONKI (CME)** — `sql/06_nasa_donki_create.sql`. Open license (public domain), same key system as NeoWs. High risk: the response is a top-level JSON array, not an object — every other source in this package returns a top-level object, and whether `CREATE LIGHTNING REST TABLE` accepts a bare array response at all is unverified. Expanded (2026-09-19) with a second view (`cme_analyses_table`) and 8 analytical queries, confirmed via `curl` against 65 real events in the script's date range — numeric fields here are real JSON numbers (no `CAST` gotcha like NeoWs), but 4 of 65 events have more than one analysis flagged `isMostAccurate`, handled with a `ROW_NUMBER()` window function. Still not yet live-tested against Zetaris.
7. **Eurostat REST API** — `sql/07_eurostat_create.sql`. Open license, with a condition (copyright policy page worth reading directly). Returns JSON-stat 2.0, a sparse multi-dimensional array format with no array-of-structs to flatten — fundamentally different from every other source's shape. **Live-tested and confirmed working end to end (2026-09-19)** — the base table, metadata view, snapshot view, full value-decode view, and all 8 example queries have all been run and verified. Found and fixed a real bug the same day: the original query's `age=Y15-74` is invalid for this dataset, silently returning empty data rather than an error (correct code is `TOTAL`). The full decode uses `from_json(to_json(...), 'map<string,TYPE>')` to coerce Spark's struct inference into a map so a dynamic-key JSON object can be exploded — confirmed working, but only once applied to *every* dynamic-key object in the query: a first attempt applied it to `value` only and plainly exploded the second one (`dimension.time.category.index`), producing a `DATATYPE_MISMATCH` that itself confirmed the `value` coercion had raised no error. This went from "highest risk, likely drop candidate" to fully working, and the coercion technique is a genuinely new, reusable pattern for this package. See `HOWTO.md`, "Troubleshooting / FAQ" for the general lesson.
8. **Statistics Canada WDS** (`getChangedCubeList`) — `sql/08_statcan_wds_create.sql`. Open license (StatCan Open Licence), no key. Simplest shape investigated across this whole batch — flat array-of-structs, one level, plain GET. **Live-tested and confirmed working (2026-09-19).** Extended with a 5-day window (one REST table per day, unioned like PokéAPI/Open Food Facts) and 8 analytical queries — found that every release in the window happens at the same time of day (08:30) and exactly 2 of 119 unique products changed on every single day. 3 of the 8 queries (3, 7, 8) initially hit the known self-join `MISSING_ATTRIBUTES` error via `WHERE ... IN (SELECT ...)` and scalar `HAVING` subqueries re-reading the same union'd view — confirming this error class isn't limited to explicit `JOIN`s (first found on Open Food Facts, `sql/03`) — fixed with window functions. Also investigated and confirmed blocked: the `getCubeMetadata` follow-up (which would give human-readable titles instead of opaque product IDs) requires a raw JSON POST body, which strictly rejects Zetaris's only confirmed body format (form-urlencoded, `415` error) — see `HOWTO.md`, "Known limitations," for the general finding (no confirmed way to send a raw JSON body in this package yet).
9. **Australian ABS Data API** (CPI) — `sql/09_abs_data_api_create.sql`. Open license (CC-BY 3.0 AU, older version, not 4.0). SDMX-JSON 2.0.0, same shape class as Eurostat but with an extra layer of compound dynamic keys. **Blocker found and fixed (2026-09-19):** the original broad `all` query (~2.4 MB) failed `CREATE LIGHTNING REST TABLE` live with a raw `TTransportException` (a transport-layer failure, not a SQL/REST error) — most likely the payload size overwhelming the connection for one fetch. Fixed by deriving real dimension codes from ABS's own `datastructure`/`codelist` endpoints (an earlier guess had 404'd) and scoping to a single series (`1.10001.10.50.Q`, ~11 KB instead of 2.4 MB). **Confirmed live in Zetaris:** the fixed `CREATE LIGHTNING REST TABLE` and `cpi_dimensions_table` view both succeeded. **Full value decode added (2026-09-19):** scoping to a single series collapsed the "two dynamic-key levels" problem to one — the outer `series` key is a single, directly-addressable key (no explode needed), the period-label array is a genuine array (`posexplode()`), and only the innermost `observations` object needs Eurostat's proven `to_json`/`from_json` coercion. `cpi_series_table` and 8 analytical queries **confirmed live in Zetaris** (2026-09-19), matching the values validated in Python against real data (46 quarters, 2015-Q1 through 2026-Q2).
10. Not included: REST Countries (now key-gated) — `countries.dev` flagged as an unverified candidate if country reference data is ever needed.
11. **JSONPlaceholder** — still not scripted (wasn't part of the 2026-09-19 investigation batch above). `https://jsonplaceholder.typicode.com/`, MIT, no signup — the flattest/simplest possible REST source, worth adding if a "get a 200 back in 30 seconds" example is still wanted after the batch above is worked through.

## Goal

Establish the confirmed `CREATE LIGHTNING REST TABLE` + `CREATE SCHEMASTORE VIEW` pattern across a wide enough range of real-world JSON shapes that every later government-API category (NASA, data.gov, EU, UK, Canada, Australia, ...) can reuse it with confidence instead of re-deriving it per category. EDGAR proved the baseline works; the 2026-09-19 investigation batch (sources 2–9) was a deliberate breadth pass — testing as many *different* shape classes as possible in one go (see `open_data/rest_apis/HOWTO.md`, "Understanding JSON response shapes") — so shape-specific problems get found and fixed (or a source gets dropped) before every remaining manifest category independently rediscovers the same issues one at a time.

## Open questions / dependencies

- The `CREATE SCHEMASTORE CONTAINER` idempotency gap is a real usability problem for this whole package, not just EDGAR — every script that creates a container needs the "comment this out on a re-run" workaround until (if) a precheck mechanism is found
- If `CREATE LIGHTNING DATABASE` turns out to share the same one-time-only limitation, that's a cross-cutting fix needed in `open_data/parquet_csv/` too, not just here
- Sources 6, 7, and 9 (DONKI, Eurostat, ABS) are the real open questions of this batch — whether Zetaris can ingest a top-level-array response, and whether SDMX-family formats are usable at all through this pattern, are answers that will shape how ambitious later categories (EU §11, Australia §12) can be
- If DONKI's top-level-array problem turns out to be a real Zetaris limitation (not just this source), that's worth checking against any *other* manifest source that returns a bare array before assuming REST tables always need object-wrapped responses
