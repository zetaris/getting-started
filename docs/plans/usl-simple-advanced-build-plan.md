## 1. Why a separate plan from `edgar-sic-enrichment-plan.md`

That plan's scope was "build the EDGAR+SIC data product using Zetaris's composition primitives available at the time" — which turned out to be `SCHEMASTORE VIEW` + a manual, SQL-free Virtual Data Mart (section 5.3 of that plan: confirmed no SQL surface exists for VDM). USL is a different primitive, introduced to this repo after that plan closed, and per `docs/guides/zetaris-sql-companion.md` section 7-8, it appears to close exactly the gap that plan had to accept as a permanent manual step. That's a distinct enough claim — "USL can fully script what VDM couldn't" — that it deserves its own build-and-verify plan rather than being folded into the closed-out original, especially since the original plan's own file should stay a historical record of what was actually built and tested at the time, not be rewritten around a primitive that didn't exist yet when it was written.

## 2. Scope: simple first, advanced second

Per the requested approach, this plan builds two USLs of deliberately different complexity, in order, so a failure on the advanced one doesn't block confirming the basic USL lifecycle works at all:

| | Simple USL | Advanced USL |
|---|---|---|
| Script | [`open_data/usl/sql/01_simple_sic_usl.sql`](../../open_data/usl/sql/01_simple_sic_usl.sql) | [`open_data/usl/sql/02_advanced_company_profile_usl.sql`](../../open_data/usl/sql/02_advanced_company_profile_usl.sql) |
| Tables | One: `sic_code` | Two, related: `company` (7 rows, one per hardcoded company) `FOREIGN KEY`-referencing `sic_code` |
| Source data reused | `company_dns.sic_codes_raw` (already live-tested, `sql/10`) | `company_dns.sic_codes_raw` + the 7 `*_submissions_raw` REST tables (already live-tested, `sql/11`) |
| DDL features exercised | `PRIMARY KEY` only | `PRIMARY KEY`, `FOREIGN KEY ... REFERENCES`, `NOT NULL` |
| DQ | One custom rule (a direct analog of `sql/10` query 8's self-consistency check) | The auto-generated FK rule, **plus** a custom rule analog of `sql/11` query 8 (description agreement — a value-equality check FK can't express) |
| Materialization | Exercised once, `Records: All` (no DQ gating needed) | Exercised once, `Records: Valid Records Only` (requires the DQ rule above to exist first, per the USL guide's own gating rule) |
| Contrast target | N/A (no simple-single-table version exists in `sql/10`/`sql/11` to contrast against — this is new ground) | `open_data/rest_apis/sql/rate_limited/11_edgar_company_profiles_create.sql` + its manual VDM walkthrough — same 7 companies, same join, different mechanism |

## 4. Verify steps (live Zetaris required — none done yet)

Work through in order; each one either confirms or corrects a specific claim in `docs/guides/zetaris-sql-companion.md` section 8, and that guide should be updated (not just this plan) as each is resolved — see section 6.

- [ ] **V0 — Namespace layout experiment.** `docs/guides/zetaris-sql-companion.md` section 8 and this plan's scripts currently assume a flat `lightning.metastore.usl_demo` namespace, kept deliberately separate from `company_dns`/`edgar` (those are SchemaStore container names, a different object entirely, not USL namespaces) — but that's a guess, not a confirmed convention, and the user has asked for it to be tested rather than taken as given. Before running V1, try **both** of the following on the live instance and record what actually happens, not just what compiles:
  - (a) the flat layout as written, `CREATE NAMESPACE IF NOT EXISTS lightning.metastore.usl_demo;`
  - (b) a nested, per-source layout, e.g. `CREATE NAMESPACE IF NOT EXISTS lightning.metastore.company_dns.sic_usl;` — does Zetaris accept a namespace nested under a name that doesn't otherwise exist as a namespace, does the ERD/USL landing page render it any differently (per the USL User Guide section 2's "namespaces nest" claim), and does either layout collide with or shadow the existing `company_dns`/`edgar` SchemaStore containers in the catalog tree?
  Pick whichever layout the experiment shows is actually preferable (fewer surprises, clearer catalog-tree presentation, or whatever else turns up) and update both `open_data/usl/sql/01_simple_sic_usl.sql` and `02_advanced_company_profile_usl.sql` to match before treating either script as more than a first draft. Record the result here and in the companion guide section 8.4, since "which namespace layout to use" is exactly the kind of thing that guide exists to settle from live behavior rather than from reading alone.
- [ ] **V1 — Namespace + simple USL compiles and deploys.** Run `01_simple_sic_usl.sql` through the `CREATE NAMESPACE` / `COMPILE USL` steps, using whichever namespace layout V0 settled on. Record whether `COMPILE USL IF NOT EXISTS` is actually idempotent on a second run (companion guide section 8.4 flags this as unconfirmed, by analogy to `CREATE SCHEMASTORE CONTAINER`'s missing `IF NOT EXISTS` in section 5).
- [ ] **V2 — Activation against a `LATERAL VIEW explode()` + `from_json`/`to_json` coercion query succeeds, with schema validation actually catching a mismatch.** First activate correctly and confirm `sic_code` gets 1,005 rows (same count as `sql/10`'s `company_dns.sic_codes_table`). Then deliberately activate a second, throwaway table with one column deliberately mistyped (e.g. declare `sic_code` as `int` instead of `varchar(4)`) and confirm the guide's claim that a schema mismatch is "reported inline in the dialog" — note in the companion guide whether the same inline reporting exists on the SQL path (`ACTIVATE USL TABLE ... AS SELECT` run from a script) or only in the GUI dialog described in the USL User Guide.
- [ ] **V3 — Custom DQ rule + `RUN DQ` on the simple USL.** Register and run the DQ rule analogous to `sql/10` query 8 (`HAVING COUNT(DISTINCT major_group_desc) > 1` becomes a per-row boolean expression suitable for `REGISTER DQ`). Confirm it returns the same "zero invalid records" result `sql/10` got, and record the exact valid/invalid/total row counts `RUN DQ` reports.
- [ ] **V4 — ⏸ DEFERRED — Materialize the simple USL, `Records: All`.** Needs a configured cloud storage target, which this repo doesn't have yet (deferred per the plan header above, not skipped permanently). Once unblocked: confirm the card-color lifecycle (grey → blue → orange/pending → purple) and the LIVE/MATERIALIZED toggle both behave as the USL User Guide describes; time a query against LIVE vs. MATERIALIZED mode as the first real data point on whether USL materialization out-performs `CACHE TABLE`'s confirmed ~40x speedup (`sql/10`, `docs/guides/zetaris-sql-companion.md` section 5), or is a different mechanism with different tradeoffs.
- [ ] **V5 — Advanced USL: FK relationship + auto-generated DQ rule.** Build `company`/`sic_code` with the FK, confirm the ERD canvas draws the relationship, and confirm a DQ rule was auto-generated for it (per the USL User Guide section 8.1's table of constraint-generated rules). Deliberately test the `cik` format mismatch noted in `sql/11` caveat 1 (bare integer vs. zero-padded string) — if the FK is defined on a mismatched pair of columns, confirm whether it fails at `COMPILE`/`ACTIVATE` time, fails silently at `RUN DQ` time, or something else. This directly resolves the risk flagged in `docs/guides/zetaris-sql-companion.md` section 8.3.
- [ ] **V6 — Advanced USL: does the FK-backed DQ rule replace `sql/11` query 8, or only partially?** This is the specific question the user asked this plan to answer. Run the auto-generated FK rule and the custom description-agreement rule side by side, and compare what each one catches against what `sql/11`'s hand-written query 8 catches (a `WHERE sic_description_edgar <> sic_description_reference` check). **Working hypothesis to confirm or refute:** the FK rule only proves *referential existence* (every company's `sic` value exists somewhere in `sic_code`); it cannot express *value equality between two independently-sourced description columns*, so the custom rule is still required and the FK rule is additive, not a replacement. Record the actual result — this hypothesis could be wrong if the USL DQ subsystem turns out to support cross-table value-equality checks that our reading of the guide's `REGISTER DQ` examples missed.
