# REST API Data Sources for Zetaris Quick-Starts

A catalog of REST API sources you can point a small Zetaris deployment at directly via `CREATE LIGHTNING REST TABLE` — no file download, the JSON response becomes a queryable table (raw) plus a flattened `SCHEMASTORE` view (tabular). Each entry lists the license, the exact endpoint pattern, a docs link, and the matching onboarding script in `sql/`. One source (Singapore's PM2.5 API) hit a blocking issue during testing and has been moved to `failure_cases/` instead — see its entry below and `failure_cases/README.md`.

**License key:** Open — use it freely (read the note for any attribution requirement) · Open, with a condition — worth reading before you build on it · Not included — see the note for why

**About the SQL:** every `CREATE LIGHTNING REST TABLE` statement registers the raw JSON response as a table; every `CREATE SCHEMASTORE VIEW` flattens it into something query-shaped via `LATERAL VIEW explode(...)`. See `HOWTO.md` for the full syntax reference and known limitations — most importantly that `CREATE SCHEMASTORE CONTAINER` can only be run once per name (no `IF NOT EXISTS` support), and that removing a source's REST table(s) requires the Zetaris Data Explorer UI, not a SQL `DROP` statement.

## 1. SEC EDGAR XBRL Company Facts API — license: ambiguous

- **What it is:** structured financial facts (revenue, and other US-GAAP tags) extracted from public companies' own XBRL-tagged filings, served as JSON per company/concept via `data.sec.gov/api/xbrl/companyconcept/CIK{10-digit-cik}/us-gaap/{tag}.json`.
- **License:** filings are filer-authored, not government-authored — free API access doesn't automatically mean a copyright/license grant over the extracted facts. Same posture as the SEC EDGAR entry in the main manifest (`quickstart-data-manifest.md` §6, which covers raw filing PDFs — this is the same underlying agency/data family, a different access method: structured XBRL facts instead of PDF documents). Practical guidance: query the live API for a demo, don't bulk-redistribute a copy of the extracted data.
- **Access:** free, no authentication, but SEC requires a declared `User-Agent` (blocks default/missing ones) and caps requests at 10/sec — see [SEC's developer FAQ](https://www.sec.gov/os/webmaster-faq#developers).
- **Docs:** [Accessing EDGAR data](https://www.sec.gov/search-filings/edgar-search-assistance/accessing-edgar-data) · [EDGAR company search](https://www.sec.gov/cgi-bin/browse-edgar) (for confirming a company's current CIK)
- **Shape:** a single JSON object per company/concept; the `units.USD` field is an array of structs (`accn`, `end`, `filed`, `form`, `fp`, `frame`, `fy`, `start`, `val`), not parallel arrays — flattens with `LATERAL VIEW explode(units.USD) AS fact` + dot-access, not `posexplode()`.
- **Live-tested (2026-09-18)** against 7 companies (Apple, IBM, Oracle, Walmart, Target, Ford, Tesla) — see `sql/01_edgar_company_facts.sql` for the known limitations this script accounts for (mixed-case field quoting, a possible response-truncation issue worth verifying per source, and the `CREATE SCHEMASTORE CONTAINER` one-time-only limitation).

## 2. PokéAPI — license: open (BSD-3-Clause) — live-tested, working

- **What it is:** structured game data (Pokémon stats, abilities, moves, types) — a large, well-modeled REST API good for showing nested JSON.
- **License:** BSD-3-Clause for the code/API — [LICENSE.md](https://github.com/PokeAPI/pokeapi/blob/master/LICENSE.md). Fair Use Policy: cache responses, don't load-test it. Pokémon names/characters are Nintendo trademarks — fine for a technical demo, not for anything Zetaris-branded.
- **Access:** no signup, no formal rate limit (removed 2018) but the Fair Use Policy still applies.
- **Docs:** [pokeapi.co/docs/v2](https://pokeapi.co/docs/v2)
- **Shape:** top-level object per Pokémon; `abilities`, `types`, and `stats` are all `array<struct<..., X:struct<name,url>>>` — array-of-structs with one extra level of nesting inside the struct.
- **Live-tested (2026-09-19):** confirmed working end to end, including the two-level dot-access through an exploded field (`ability.ability.name`) that was the open question in the original script — this was the first confirmation in this package that Zetaris supports nested-struct access more than one level deep through `LATERAL VIEW explode()`, which derisks similarly-shaped sources elsewhere (e.g. NASA NeoWs, `sql/05`).
- **Extended to two Pokémon** (Pikachu, Charizard) with `abilities`/`types`/`stats` views each, plus three cross-Pokémon `UNION ALL` views and six example analytical queries (base-stat totals, a side-by-side stat comparison, hidden-ability lookup, full per-Pokémon profile) — see `sql/02_pokeapi.sql`.
- **Full script live-tested (2026-09-18):** every CREATE and all 6 example queries confirmed working. `DROP VIEW` in the `TEARDOWN` block is confirmed working. `DROP TABLE` and `DROP DATASOURCE` ran without raising an error at the time, but do not actually remove the underlying REST tables or Lightning database registration — see `HOWTO.md`, "Removing a source", for the full explanation and the Data Explorer path that does work.

## 3. Open Food Facts — live single-product API — license: open, with a condition (ODbL)

- **What it is:** the live per-product lookup API, distinct from the bulk CSV/JSONL export already onboarded as a filestore source in `../parquet_csv/` — this demonstrates the single-record REST pattern specifically.
- **License:** ODbL — same as the bulk-export entry in `../parquet_csv/parquet-csv-data-sources.md`. Attribution required, share-alike if redistributing a combined database.
- **Access:** no signup, but requires a custom `User-Agent`; per-endpoint rate limits apply.
- **Docs:** [openfoodfacts.github.io/openfoodfacts-server/api](https://openfoodfacts.github.io/openfoodfacts-server/api/)
- **Shape:** top-level object wrapping a `product` struct; `product.ingredients` is array-of-structs with sparse/optional fields (not every ingredient has the same fields present) — tests Zetaris's tolerance for inconsistent struct shapes across array elements. `product.nutriments` is a separate flat struct (no array, no `explode()` needed) with several hyphenated field names (`energy-kcal_100g`) needing backtick-quoting.
- **Extended (2026-09-18)** to four products picked for contrasting nutrition profiles — Nutella, Coca-Cola, Prince biscuits, and Barilla Pesto alla Genovese — each with a `_nutrition_table` (nutri-score, nova group, calories/fat/sugar/salt/protein per 100g) and `_ingredients_table` view, plus two cross-product `UNION ALL` views and 8 analytical queries: sugar/calorie ranking, a nutri-score-ordered health snapshot, a "% of calories from sugar" normalized comparison, per-product ingredient count and vegan share, ingredients shared across unrelated brands, an oil-family ingredient search, each product's single dominant ingredient, and a saltiest-product-vs-ingredient-count join. Also surfaced a new shape wrinkle: Prince's ingredients array has doubly-nested compound entries (a "Céréale" ingredient wrapping its own wheat-flour/whole-wheat-flour sub-ingredients) — not flattened here, same class of open question as PokéAPI's `moves` field.
- **Partially live-tested (2026-09-18):** queries 1-7 confirmed working. Query 7 originally attempted a self-join of a `UNION ALL`'d exploded view against an aggregate subquery of itself, which failed with `MISSING_ATTRIBUTES.RESOLVED_ATTRIBUTE_APPEAR_IN_OPERATION` — a Zetaris/Spark analyzer limitation, not a SQL mistake; fixed and confirmed working by rewriting as a `ROW_NUMBER() OVER (...)` window function instead, returning exactly one dominant-ingredient row per product (Coca-Cola/carbonated water 83.4%, Nutella/sugar 52.16%, Pesto/sunflower oil 34.94%, Prince/Céréale 47.75%). See `HOWTO.md`, "Troubleshooting / FAQ", for the general pattern to avoid. Query 8 not yet reached.
- **Teardown investigation (2026-09-18):** `DROP VIEW` statements all succeeded. `DROP TABLE off_live_rest.nutella_product` failed with `NoSuchElementException: key not found: off_live_rest`, deep in Spark's native catalog fallback path. `DROP DATASOURCE OFF_LIVE_REST` then failed too, with `Data Source : 'OFF_LIVE_REST' doesn't exist` — and cross-checking the Zetaris Data Explorer showed PokéAPI's `POKEAPI_REST` still listed under "File Source & API" despite its own `DROP DATASOURCE` reporting no error earlier. Conclusion: `DROP DATASOURCE` does not work on a `CREATE LIGHTNING DATABASE`-registered source — it appears to be written only for JDBC-style `CREATE DATASOURCE` registrations, per both the legacy and current Zetaris SQL manuals. There is no SQL alternative for removing this registration; see `HOWTO.md`, "Removing a source", for the confirmed Data Explorer path.

## 4. Singapore data.gov.sg — PM2.5 real-time API — license: open (SODL v1.0) — BLOCKED, see `failure_cases/`

- **What it is:** national air-quality readings (PM2.5), updated hourly, part of data.gov.sg's real-time API family (same family as weather forecasts, rainfall, tide/temperature readings).
- **License:** Singapore Open Data Licence (SODL) v1.0 — same umbrella license as the pulled-forward data.gov.sg CSV source in `../parquet_csv/`.
- **Access:** no key or headers needed for testing — confirmed a plain GET with no `User-Agent` or auth returns 200. Documented as 5 requests/minute, but the real burst limit is tighter: repeated testing tripped a 429 after roughly 5-6 requests within 5-8 seconds, recovering after about 30 seconds.
- **Docs:** [guide.data.gov.sg/developer-guide/real-time-apis](https://guide.data.gov.sg/developer-guide/real-time-apis)
- **Shape:** top-level object; the array-of-structs field (`data.items`) is nested one level under a non-array `data` wrapper (not at the top level like EDGAR/PokéAPI), and each item's per-region breakdown is a fixed struct, not an array — a genuinely different shape class from every other source in this package.
- **Extended (2026-09-19)** from a single latest reading to a full day of hourly readings (24 items) using the endpoint's `?date=YYYY-MM-DD` parameter, plus a region reference view (name, latitude, longitude) flattened from `data.regionMetadata`, a long-format cross-region view (one row per timestamp/region pair, the same `UNION ALL` pattern as PokéAPI's and Open Food Facts' cross-record views), and 8 analytical queries: full 24-hour trend, per-region daily average/min/max, the single worst and cleanest readings of the day, a computed hourly "national" average, hours spent above a health-relevant threshold, an hour-by-hour worst-region ranking via window function, and a join against the region reference view for geographic context.
- **Bug found and fixed during this expansion:** the original script selected a `pm25_one_hourly.national` field that does not exist anywhere in the real API response (confirmed by inspecting every key across a full day of readings) — the endpoint only ever returns the 5 regional readings, no separate national figure. Removed; a national-level figure is now computed as an average across the 5 regions instead (see query 5).
- **Blocked (2026-09-19):** `CREATE LIGHTNING REST TABLE`, the first statement in the script, returned an HTTP 502 in the Zetaris SQL Workspace, with no other query run first. Independent `curl` testing confirmed the API is reachable, needs no special headers or auth, and doesn't have this problem on its own — the leading (unconfirmed) hypothesis is that this specific source's tight rate limit is being tripped by more than one request per statement on the Zetaris side. Moved to `failure_cases/singapore_pm25/` with the full investigation in `failure_cases/singapore_pm25/ISSUE.md`, since the other 8 sources already cover the JSON-shape range this package needs. See `HOWTO.md`, "Troubleshooting / FAQ", for the general "HTTP 502" entry this case is documented under.

## 5. NASA NeoWs (Near Earth Object Web Service) — license: open (public domain) — live-tested, working

- **What it is:** structured asteroid/near-Earth-object data — this script uses `/neo/browse` (a flat, paginated catalog) rather than `/neo/rest/v1/feed` (whose response is keyed by date string, a shape LATERAL VIEW explode() isn't built for).
- **License:** NASA content is a U.S. federal government work, public domain (17 U.S.C. §105).
- **Access:** `DEMO_KEY` works with no signup (30 req/hour, 50/day/IP); a free `api.data.gov` key raises this to 1,000 req/hour. Confirmed (2026-09-19) this endpoint does not exhibit the aggressive burst-throttling found on Singapore's PM2.5 API (`failure_cases/`) — 6 rapid-fire requests all returned 200.
- **Docs:** [api.nasa.gov](https://api.nasa.gov/)
- **Shape:** top-level object; `near_earth_objects` is array-of-structs, deeply nested (3 levels for `estimated_diameter.kilometers.estimated_diameter_min`), plus a nested array-within-array (`close_approach_data`) requiring either array-indexing or a second `explode()`.
- **Live-tested (2026-09-19):** base table and its first flattened view (`neo_browse_table`, one row per object with its earliest recorded approach) confirmed working end to end.
- **Extended (2026-09-19)** with a second view, `neo_close_approaches_table`, built with the previously-optional double-`explode()` pattern (one row per object per recorded approach, past and predicted future, out to the year 2187 for some objects), and 8 analytical queries: largest objects by diameter, hazardous asteroids ranked by size, an average-diameter hazardous-vs-not comparison, most-tracked objects by approach count, the single closest and fastest approaches on record, each object's own closest approach via a window function, and a look at upcoming predicted approaches for hazardous objects.
- **Type gotcha found and handled:** `miss_distance.kilometers` and `relative_velocity.kilometers_per_hour` are JSON strings in the raw response (e.g. `"47112732.928149391"`, quoted), while `estimated_diameter_min/max` and `absolute_magnitude_h` are real JSON numbers. Every view and query that sorts or aggregates by the string-typed fields uses an explicit `CAST(... AS DOUBLE)` — without it, Zetaris would very likely infer STRING and sort lexicographically, giving wrong "closest approach" results (e.g. a 9,000,000 km distance sorting before a 47,000,000 km one because `'9' > '4'` as characters).
- **Rate-limit finding (2026-09-19):** running the full script (verification queries plus all 8 example queries) hit NASA's DEMO_KEY hourly cap partway through, with the `429 OVER_RATE_LIMIT` error surfacing on an ordinary `SELECT` well after `CREATE LIGHTNING REST TABLE` had already succeeded — direct proof that a Lightning REST table re-issues its HTTP request on every query, not once at creation. See `HOWTO.md`, "Troubleshooting / FAQ", for the full writeup and the (unconfirmed) `CACHE TABLE` workaround now included in the script.
- **Recommendation: register a free API key.** DEMO_KEY's 30 req/hour (50/day) is easy to exhaust running this script's full query set, and this quota is shared with `sql/06_nasa_donki.sql`. Register directly at [api.nasa.gov](https://api.nasa.gov/) — First Name, Last Name, Email, key emailed back immediately, no approval wait — for 1,000 req/hour (confirmed 2026-09-19). The limit resets on a rolling basis per key, so if you're stuck on DEMO_KEY, the wait after hitting the cap is up to an hour from your first request in the window, not a short pause. Testing whether `CACHE TABLE` actually fixes the repeat-request behavior needs a registered key's larger budget to do properly.

## 6. NASA DONKI (Space Weather) — license: open (public domain) — high risk

- **What it is:** Coronal Mass Ejection (CME) space-weather events, queryable by date range.
- **License:** same NASA public-domain basis as NeoWs.
- **Access:** same `api.data.gov` key system as NeoWs.
- **Docs:** [api.nasa.gov](https://api.nasa.gov/) (DONKI section)
- **Shape:** top-level JSON array, not an object — every other confirmed or scripted source in this package returns a top-level object. Whether `CREATE LIGHTNING REST TABLE` can register a table from a bare array response at all is unverified — this is the first thing to test, before the flattening logic.
- **Extended (2026-09-19)** with two views (`cme_instruments_table`, `cme_analyses_table`, the latter promoted from a previously-commented-out optional block) and 8 analytical queries: total event count and date range, the 5 fastest CMEs (deduplicated per event via a window function), a speed-classification (S/C/O/R/ER) breakdown, most-observed events by instrument count, events needing multiple analyses, a solar-hemisphere breakdown of source regions, daily event frequency, and full detail on the single fastest event via a cross-view join. Confirmed via `curl` against the exact date range the script uses (2026-09-01 to 2026-09-16): 65 real CME events, not empty — and unlike NASA NeoWs (`sql/05`), the numeric fields here (`speed`, `latitude`, `longitude`, `halfAngle`) are real JSON numbers, not quoted strings, so no `CAST` gotcha applies to this source.
- **Data quirk found:** 4 of the 65 events in this date range have more than one `cmeAnalyses` entry flagged `isMostAccurate: true` simultaneously — a naive filter on that flag alone can return two rows for one event. The "fastest CME" queries use a `ROW_NUMBER()` window function instead to guarantee one row per event.
- **Still not yet live-tested against Zetaris.** A first attempt (2026-09-19) failed on `CREATE LIGHTNING REST TABLE` with a `429 OVER_RATE_LIMIT` — but this is the shared-DEMO_KEY-quota problem confirmed on NASA NeoWs (`sql/05`), not an answer to this source's own open question. The top-level-array question (above) remains genuinely unresolved and blocked until a registered API key is used — see `sql/05`'s caveat 9 and `HOWTO.md`, "Troubleshooting / FAQ".

## 7. Eurostat REST API — license: open, with a condition (see below) — live-tested and working, including a full value-decode

- **What it is:** EU statistical data (e.g. unemployment rate, HICP inflation) via a fully public SDMX/REST API.
- **License:** Eurostat's copyright policy is generally understood to align with CC-BY 4.0 — the policy page itself is worth reading directly, not independently confirmed as a hard match.
- **Access:** no key, no registration, CORS-enabled.
- **Docs:** [Eurostat API Statistics guide](https://wikis.ec.europa.eu/display/EUROSTATHELP/API+Statistics+-+data+query)
- **Shape:** JSON-stat 2.0 — a sparse, multi-dimensional array format (not row-oriented JSON at all). Values are addressed by a computed flat offset key across every dimension, decoded against separate `dimension` metadata. No array-of-structs anywhere to `explode()`.
- **Live-tested (2026-09-19):** the base REST table and a metadata-only view (dataset label/source/updated, geo labels, time index map) both confirmed working end to end in Zetaris.
- **Bug found and fixed (2026-09-19):** the original query used `age=Y15-74`, an invalid code for this dataset — Eurostat doesn't error on this, it silently returns zero valid categories for that dimension and an empty `value: {}`, which looks identical to "no data collected." The actual valid codes are `TOTAL`, `Y_LT25`, `Y25-74`; fixed to `age=TOTAL`, confirmed via `curl` to return 355 real, contiguous monthly values (Poland's seasonally-adjusted unemployment rate, 1997-01 through 2026-07).
- **Expanded (2026-09-19)** in two tiers of risk: (1) a low-risk snapshot view pulling three specific known-present time indices via direct backtick-quoted dot-access (no `explode()` needed at all), backing 2 queries (long-run and year-over-year change) that don't depend on solving the harder decoding problem; (2) an experimental full-series view using `from_json(to_json(...), 'map<string,TYPE>')` to coerce Spark's default STRUCT inference for dynamic-key JSON objects back into a MAP so it can be exploded — backing 6 further queries (full series, historic min/max, recent 12-month trend, decade averages, a milestone query) if it works.
- **Confirmed working end to end (2026-09-19):** the coercion technique works. A first attempt applied it only to the sparse `value` object and plainly exploded the second dynamic-key object (`dimension.time.category.index`) without the same coercion, producing a `DATATYPE_MISMATCH` on that second explode while the `value` coercion itself raised no error in the same query plan. Fixed by applying the identical coercion to both — confirmed live: `une_rt_m_pl_series_table` returns all 355 rows, matching the count and values found via `curl` during investigation. All 8 example queries have been run and verified. See `sql/07_eurostat.sql` caveat 6c and `HOWTO.md`, "Troubleshooting / FAQ", for the general lesson (apply the coercion to *every* dynamic-key object you explode, not just the first one) — this is a genuinely new, reusable technique worth trying on other JSON-stat/SDMX sources in this package (e.g. ABS, `sql/09`).
- **Not yet live-tested; investigation also didn't find a dimension-code combination that returned populated values** (one dataset tried turned out to be discontinued) — see `sql/07_eurostat.sql`.

## 8. Statistics Canada Web Data Service (WDS) — license: open (StatCan Open Licence) — live-tested and working

- **What it is:** `getChangedCubeList` — a discovery endpoint listing which StatCan datasets ("cubes") recently published new data.
- **License:** Statistics Canada Open Licence — same permissive family as OGL-Canada 2.0; don't combine with other sources to re-identify individuals.
- **Access:** no key or registration, 50 req/sec system-wide / 25/sec per IP.
- **Docs:** [statcan.gc.ca/en/developers/wds/user-guide](https://www.statcan.gc.ca/en/developers/wds/user-guide)
- **Live-tested and confirmed working (2026-09-19):** the base REST table and `changed_cubes_table` view both confirmed in Zetaris.
- **Extended (2026-09-19)** to a 5-day window (2026-09-14 through 2026-09-18, one REST table per day, unioned into `changed_cubes_all_table` — the same per-record-group-then-union pattern as PokéAPI and Open Food Facts) with 8 analytical queries: daily change volume, a busiest/quietest day ranking via window function, which products change on every single day in the window ("daily cubes," found programmatically), an update-frequency distribution, total activity summary, a check on StatCan's fixed daily release schedule, full history for the daily cubes, and a spot-check of one-off changes. Two real findings from the investigation: every release in the window happened at exactly the same time of day (08:30), and of 119 unique products touched, exactly 2 changed on all 5 days while the rest changed on only one.
- **Investigated and blocked (2026-09-19):** the natural follow-up, `getCubeMetadata` (which would replace opaque `productId` numbers with human-readable titles), is a POST requiring a raw JSON array body. Confirmed via `curl` that it strictly rejects a form-urlencoded body (`415 Unsupported Media Type`) — the only body format ever confirmed to work with Zetaris's `BODY(...)` clause in this package. There is no confirmed way to send a raw JSON body through the established `REQUEST(...)`/`BODY(...)` pattern, so this endpoint remains out of reach until that's resolved (e.g. an untested `http_encoding "JSON"` option). See `sql/08_statcan_wds.sql` caveat 3.
- **Self-join bug hit and fixed (2026-09-19):** 3 of the 8 example queries (3, 7, 8) initially failed with `MISSING_ATTRIBUTES.RESOLVED_ATTRIBUTE_APPEAR_IN_OPERATION` — each referenced `changed_cubes_all_table` more than once via a `WHERE ... IN (SELECT ...)` or scalar `HAVING` subquery. This is the same self-reference class already confirmed on Open Food Facts (`sql/03`), now also confirmed to trigger via subquery forms, not just an explicit `JOIN`. Fixed by rewriting all three with `COUNT(*) OVER (PARTITION BY product_id)` window functions instead of any subquery re-reading the same view. See `HOWTO.md`, "Troubleshooting / FAQ," for the updated general guidance.
- **Shape:** top-level object wrapping a plain, flat array-of-structs (`object: [{productId, releaseTime, responseStatusCode}, ...]`) — the simplest shape found across every source investigated in this pass. Good smoke test if a more complex source is failing.

## 9. Australian Bureau of Statistics (ABS) Data API — license: open (CC-BY 3.0 AU)

- **What it is:** Australian economic/statistical data (this example: CPI) via ABS's SDMX-based Data API.
- **License:** CC-BY 3.0 Australia by default (the older 3.0 port, not 4.0 — same caveat already known from the main manifest).
- **Access:** no API key required.
- **Docs:** [ABS Data API user guide](https://www.abs.gov.au/statistics/application-programming-interfaces-apis/data-api-user-guide/using-api)
- **Shape:** SDMX-JSON 2.0.0 (data-message format) — same shape class as Eurostat but with an extra layer: `dataSets[0].series` is keyed by a colon-separated dimension-index tuple, and each series' `observations` is itself keyed by a further time-index.
- **Blocker found and fixed (2026-09-19):** the script's original endpoint used the broad `all` query (~2.4 MB, every dimension combination for the whole CPI dataflow), which failed its `CREATE LIGHTNING REST TABLE` statement live with a raw `TTransportException` — a low-level transport failure, not a SQL or REST error. Most likely cause: the payload size overwhelming the transport layer for one fetch, consistent with the size already having been flagged as a concern before this was tested. Fixed by deriving real (not guessed) dimension codes directly from ABS's own `datastructure`/`codelist` endpoints — a naive earlier guess (`M1.AUS.10001.Q`) had 404'd — giving a properly-scoped query (`1.10001.10.50.Q`, Australia/all-groups/original/quarterly from 2015-Q1) that returns a single real, populated series in ~11 KB instead of 2.4 MB. **Confirmed live in Zetaris:** the fixed `CREATE LIGHTNING REST TABLE` and the `cpi_dimensions_table` view both succeeded (`SELECT * FROM abs_data.cpi_dimensions_table;` returned real dimension metadata).
- **Full value decode added and confirmed live in Zetaris (2026-09-19):** scoping the query to a single series turns out to collapse ABS's "two dynamic-key levels" problem to effectively one — the outer `series` object has exactly one key (`` `0:0:0:0:0` ``, addressable directly via backtick dot-access, no explode needed) once every non-time dimension is fixed to a single code; the period-label array is a genuine JSON array (`posexplode()`, no coercion); only the innermost `observations` object needs the Eurostat-proven `from_json(to_json(...), 'map<string,array<double>>')` coercion. `cpi_series_table` and all 8 analytical queries (full series, min/max, QoQ via `LAG()`, YoY via `LAG(..., 4)`, annual averages, recent 8 quarters, cumulative growth via `FIRST_VALUE`/`LAST_VALUE`, direction distribution) are confirmed working end to end, matching the values validated against real ABS data in Python (46 quarters, 2015-Q1=74.16 through 2026-Q2=102.31, matching real-world Australian CPI trends) — see `sql/09_abs_data_api.sql`.

## 10. company_dns — SIC hierarchy reference — license: Apache 2.0

- **What it is:** a company-firmographics/industry-classification service (`github.com/miha42-github/company_dns`) that, among other things, serves the full US Standard Industrial Classification (SIC, 1987 revision) hierarchy — 4-digit code, description, and its division/major-group/industry-group rollup — as REST/JSON. Found via a direct pointer from the repo owner, not open search; see `docs/plans/edgar-sic-enrichment-plan.md` secs 4, 4.3 for the open alternatives that were checked and rejected first (SEC's own flat HTML list, a flat GitHub JSON mirror, OSHA's SIC Manual with a real hierarchy but no API, commercial APIs, and the UK's differently-coded SIC system).
- **License:** the service itself is Apache 2.0. Its SIC data traces back to SEC's own public SIC list (`dependencies.data.sicData` in every response) — same "query live, don't bulk-redistribute the extracted data" posture already applied to the raw EDGAR entries elsewhere in this package.
- **Access:** hosted instance at `https://company-dns.mediumroast.io`, no key or signup; also self-hostable via Docker at `http://localhost:8000`. No documented rate limit — but see the cold-start finding below, a different constraint entirely.
- **Docs:** interactive API reference at `/docs` on the hosted instance; OpenAPI spec at `/openapi.json`.
- **Shape:** top-level object with a dynamic-key ("map-shaped") field (`data.sics`, keyed by SIC code) — same shape class as Eurostat/ABS (sources 7, 9), decoded with the same `from_json(to_json(...), 'map<string, STRUCT<...>>')` coercion, confirmed working here too.
- **Undocumented bulk-retrieval trick found (2026-09-21):** reading the service's own source (`lib/sic.py`) showed every SIC lookup is a SQL `LIKE '%query%'` substring match with no length floor on the code parameter — so a single literal `%` (URL-encoded `%25`) matches every row, pulling the entire 1,005-code SIC list in one call instead of one call per code or per company. Confirmed live: this one endpoint already carries everything needed (full hierarchy denormalized onto every row) — the 3 sibling endpoints (division/major/industry) were checked and found fully redundant for this use case, so only `/sic/code/%25` is called in `sql/10_company_dns_sic.sql`.
- **Cold-start 502s, confirmed and reproduced 5+ times (2026-09-20/21):** the hosted instance appears to scale to zero between requests — the first request after idle time returns an empty response or an HTTP 502, resolving cleanly on immediate retry. This is a different cause from Singapore PM2.5's rate-limit-driven 502 (source 4) and can surface as a client-side `TTransportException` rather than a raw 502 if it happens on a `SELECT` rather than `CREATE LIGHTNING REST TABLE` (a REST table re-fetches on every query — see HOWTO.md, "Known limitations"). Fix: `scripts/warmup_company_dns.ts`, a small Deno script that polls `/health` until warm before touching the real endpoint — see `open_data/rest_apis/scripts/`.
- **`CACHE TABLE` confirmed working (2026-09-21) — the first such confirmation in this entire package.** An uncached `SELECT COUNT(*)` against the raw REST table took `Query Time: 49.685s`; after `CACHE TABLE`, the identical query dropped to a stable ~1.2s across repeated runs (~40x faster). Every earlier attempt to test this (NASA NeoWs, source 5) was blocked by a rate limit before the test could run — `company_dns` had no such constraint, which is what made the test possible here.
- **Live-tested and confirmed working end to end (2026-09-21):** `CREATE LIGHTNING DATABASE`, `CREATE LIGHTNING REST TABLE`, `DESCRIBE`, `SELECT COUNT(*)`, `CACHE TABLE`, the `SCHEMASTORE VIEW` (`sic_codes_table`, using the same `from_json(to_json(...))` decode technique already proven on Eurostat/ABS), and all 8 analytical queries (overview counts, per-division/per-major-group breakdowns, industry-group diversity, two description-search examples, a `ROW_NUMBER()` "one representative code per division" window function, and a data-quality self-consistency check) all confirmed working against a live Zetaris instance, post-cache.
- **Also found, not yet used:** two per-company endpoints (`/na/company/edgar/firmographics/{cik}`, merging EDGAR + this same SIC hierarchy in one call; `/na/companies/edgar/ciks/{name}`, fuzzy name-to-CIK lookup) — see `docs/plans/edgar-sic-enrichment-plan.md` sec 4.2. Not built into `sql/10` (scoped to the SIC reference data on its own); the plan's next step is joining this table's `sic_codes_table` against each EDGAR company's own `sic` field (from `data.sec.gov/submissions/CIK{cik}.json`), not calling `company_dns` per company.
